# Как получать изменения автора и не терять наши

## Устройство Git

- `origin` — наш форк `https://github.com/pitpamyati-netizen/ff14-accessibility.git`.
- `upstream` — исходный проект `https://github.com/derbruedi/ff14-accessibility.git`.
- `feature/russian-accessibility-recovery` — рабочая ветка наших дополнений.
- С 29 сентября 2026 она также выбрана главной веткой форка на GitHub:
  главная страница показывает русскую версию. Выпуски описаны в `RELEASES.md`.
- `origin/main` хранит основу автора. Наш код находится в отдельной ветке.
- `recovery/local-6.08.61` — первый восстановленный снимок. Не передвигать эту метку.

Локальные настройки Git: отправка по умолчанию в `origin`, `pull.ff=only`,
`fetch.prune=true`, `core.autocrlf=false`, `core.whitespace=cr-at-eol`.
Автор коммитов взят из активной учётной записи GitHub, почта — её `noreply`-адрес.
Секреты не записаны в проект; для HTTPS используется `gh auth git-credential`.
Глобальные настройки других проектов не менялись.

## Обновление — только по запросу пользователя

1. Прочитать `CURRENT_STATE.md` и карту дополнений. Осмотреть текущие изменения.
   Если есть незавершённая работа, сначала сохранить её отдельным коммитом или
   проверенной резервной копией. Не использовать `reset --hard` и `clean` для уборки.
2. Получить историю автора: `git fetch upstream --tags`.
3. Посмотреть новые коммиты и файлы: `git log HEAD..upstream/main --oneline`
   и `git diff --stat HEAD...upstream/main`.
4. Создать отдельную ветку обновления от текущей нашей ветки, например
   `git switch -c sync/upstream-YYYYMMDD`.
5. Выполнить `git merge upstream/main`. Разобрать каждое пересечение по смыслу:
   автоматический выбор всей «нашей» или всей «их» версии файла запрещён как способ
   разрешения сложного конфликта. Опираться на `LOCAL_CHANGES.md` и проверки.
6. Проверить `git merge-base --is-ancestor upstream/main HEAD`: успех подтверждает,
   что история автора входит в результат. Это не заменяет проверку логики.
7. Сравнить нашу ветку до объединения с итогом, объяснить каждое удаление исходника
   или функции. Убедиться, что русские таблицы, файлы `V19`, типы ремесленных действий,
   чтение материалов и проверка переноса предметов сохранены.
8. Выполнить `Build-Local.ps1`, `Test-Local.ps1`, `Package-Local.ps1`.
   Проверить `git diff --check`, состав отправляемых файлов и результаты в игре.
9. Обновить документы. Отправить разрешённую пользователем ветку в `origin`.
   PR автору создавать, если пользователь просит передать изменения автору.
   Пока обязательные сценарии в игре не проверены, честно описать ограничения
   и оставить такой PR черновиком.

## Чего не делать

### Отдельный возврат автонавигации — 3 октября 2026

Пользователь прямо потребовал полностью заменить нашу переработку автонавигации
реализацией автора и отправить результат в форк. Это отдельный перенос
навигационной части, а не полное объединение проекта с upstream.
Источник — `upstream/main` на `e006e9de6aefc4f7b6246782f225fa52389e3b63`.
Затронутые исходники сохранены в `.recovery/author-navigation-20261003`;
остальные локальные функции не заменяются файлами автора.
`AUTHOR_NAVIGATION.json` закрепляет исходные файлы и методы, а
`Test-AuthorNavigation.ps1` проверяет их перед выдачей. История форка сохраняется;
удаление нашей переработки выполняется новым коммитом, без переписывания истории.

- Не копировать ZIP автора поверх рабочей папки целиком: ZIP не решает конфликты.
- Не считать больший номер нашей сборки признаком отсутствия новых изменений автора.
- Не отправлять локальные сборки, личные логи, настройки игры и материалы `.recovery`.
- Не приписывать восстановленным файлам выдуманные прежние даты и авторов коммитов.
- Не запускать `scripts/Install-GitHooks.ps1` без чтения существующих правил:
  это авторский инструмент, он меняет локальные обработчики Git.

## Возврат к исходным файлам

Первый коммит восстановления содержит исходные файлы 6.08.61 без наших последующих
исправлений. Для просмотра достаточно `git show recovery/local-6.08.61:ПУТЬ`.
Для независимой копии можно экспортировать метку через `git archive` в отдельную
папку. Полная резервная копия до организации включает также все старые ZIP и сборки;
её расположение записано локально в `.local/recovery.json`.

Для переноса на другой компьютер клонировать наш форк и явно выбрать рабочую ветку.
Ветка `main` форка сама по себе наших дополнений не содержит.
